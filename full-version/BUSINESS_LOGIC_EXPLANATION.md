# وصف مشروع Fix-It — المرجع الشامل

> هذا الملف هو المرجع الأساسي للمشروع بالكامل. يغطي جميع الأطراف، الصلاحيات، دورة حياة الطلب، المنطق المالي، وكل التفاصيل اللازمة للبرمجة.

---

## أولاً: نظرة عامة على المشروع

Fix-It منصة SaaS من نوع **B2B2C**، تعمل كوسيط بين مراكز الصيانة والعملاء. المنصة لا تقدم خدمة صيانة مباشرة، بل توفر البنية التحتية التشغيلية والمالية لمراكز الصيانة المستقلة.

### نموذج العمل

- المنصة تستقطب شركات صيانة (مراكز) وتمنحها نظام إدارة متكامل.
- كل مركز يدير عملياته بشكل مستقل من خلال لوحة تحكم خاصة به.
- العملاء يتواصلون مع المنصة عبر API (تطبيق جوال مستقبلاً)، وتوجّه طلباتهم للمركز المناسب.
- المنصة تكسب عمولة على كل طلب مكتمل.

## ثانياً: الأطراف والمستخدمون (Actors)

المشروع يحتوي على **ستة أطراف** رئيسية، كل طرف له صلاحيات وواجهة مختلفة:

### 1. السوبر أدمن (Super Admin)

مالك المنصة. واجهة واحدة مركزية يرى منها كل شيء يحدث في جميع المراكز. لا يتعامل مع العملاء مباشرةً، لكنه يتحكم في الإعدادات العامة ويراقب الأداء المالي للمنصة بأكملها.

### 2. أدمن المركز (Center Admin)

مدير شركة الصيانة المنضمة للمنصة. يدير مركزه بشكل مستقل من خلال لوحة تحكم خاصة بمركزه فقط. لا يرى بيانات المراكز الأخرى.

### 3. موظف المركز (Center Staff)

موظفون داخل المركز يمكن لأدمن المركز تعيينهم وتحديد صلاحياتهم. مثلاً: موظف مختص بالحجز فقط، أو موظف إداري.

### 4. الفني (Technician)

منفذ الطلبات الميدانية. تابع لمركز واحد فقط. يرى ويتفاعل فقط مع الطلبات المعيّنة له شخصياً.

### 5. موظف الكول سنتر (Call Center Agent)

موظف تابع للمنصة (ليس للمراكز). مهمته الأساسية إجراء مكالمات المتابعة مع العملاء بعد اكتمال الطلبات.

### 6. العميل (Customer) — عبر API

يتفاعل مع المنصة عبر API فقط. في المرحلة الأولى يكون الطلب يُنشأ يدوياً من السوبر أدمن أو أدمن المركز، وفي المرحلة القادمة يكون للعميل تطبيق مستقل.

## ثالثاً: لوحة تحكم السوبر أدمن

هذه اللوحة تُرى **كل شيء** عبر جميع المراكز. لا توجد قيود جغرافية أو تنظيمية على ما يراه السوبر أدمن.

### أ. إدارة المراكز

- **عرض جميع المراكز:** الاسم، حالة المركز (نشط / موقوف)، تاريخ الانضمام، نسبة العمولة.
- **إضافة مركز جديد:** يسجل بيانات المركز ويحدد نسبة العمولة الخاصة به.
- **تعديل بيانات المركز:** شامل تعديل نسبة العمولة، وهي الوحيدة المخولة بذلك.
- **تفعيل / تعطيل مركز يدوياً:** بغض النظر عن الإيقاف التلقائي.
- **عرض تفاصيل مركز بعينه:** كل طلباته، فنييه، محفظته المالية، وتسوياته.

### ب. إدارة الطلبات (Global)

- عرض **جميع الطلبات** من جميع المراكز مع إمكانية الفلترة (بالمركز، الحالة، التاريخ، نوع الجهاز، المنطقة الجغرافية).
- إنشاء طلب جديد وتحديد المركز المناسب له يدوياً.
- تغيير المركز المعيّن لطلب ما (إعادة توزيع).
- تعيين فني لأي طلب في أي مركز.
- عرض التاريخ الكامل لكل طلب (من أنشأه، متى تغيرت الحالات، من عيّن الفني).

### ج. الإدارة المالية (Global)

- **لوحة المحافظ:** عرض محفظة كل مركز (إجمالي التحصيل، المستحق للمنصة، الصافي).
- **التسويات:** إنشاء تسوية لأي مركز (تحصيل المستحق أو دفع مستحقات المركز)، وعرض تاريخ جميع التسويات.
- **إجمالي إيرادات المنصة:** مجموع العمولات من جميع المراكز.
- **صافي ربح المنصة:** إجمالي العمولات − رواتب الموظفين − المصاريف التشغيلية.
- **تقارير مالية:** يومية، شهرية، سنوية، مع إمكانية التصدير.

### د. إدارة موظفي المنصة (HR)

- إضافة وتعديل وإلغاء تفعيل حسابات موظفي الكول سنتر والمحاسبين.
- إدارة رواتبهم الشهرية مع البدلات والخصومات.
- تسجيل المصاريف التشغيلية للمنصة (إيجار، كهرباء، إعلانات، إلخ).

### هـ. نظام المتابعة (Global View)

- عرض قائمة المتابعات من جميع المراكز مدمجة في مكان واحد.
- تعيين محاولات المتابعة لموظفي الكول سنتر.
- عرض تاريخ المتابعات والتقييمات.

### و. الإعدادات العامة

- **مدة المتابعة:** عدد الأيام بعد اكتمال الطلب قبل ظهور العميل في قائمة المتابعات (مثلاً: 3 أيام).
- **حد الإيقاف التلقائي:** المبلغ الذي إذا تجاوزه "المستحق للمنصة" لمركز ما دون سداد، يُوقف المركز تلقائياً.
- إعدادات أخرى عامة (العملة، المنطقة الزمنية، إلخ).

## رابعاً: لوحة تحكم المركز

كل مركز له **لوحة تحكم مستقلة** لا يرى من خلالها أي بيانات تخص المراكز الأخرى. البيانات محصورة بالكامل داخل نطاق المركز.

### أ. إدارة الفنيين

- **إضافة فني جديد:** الاسم، رقم الهاتف، التخصص (نوع الأجهزة التي يتقنها)، المنطقة الجغرافية التي يغطيها.
- **تعطيل / تفعيل فني:** الفني المعطّل لا يظهر كخيار عند تعيين الطلبات.
- **عرض أداء الفني:** عدد الطلبات المكتملة، متوسط وقت الاستجابة، متوسط تقييماته من المتابعات.
- **إدارة جدول الفني:** الأيام المتاحة وساعات العمل (يُستخدم مستقبلاً في الجدولة التلقائية).

### ب. إدارة موظفي المركز

- أدمن المركز يمكنه إضافة موظفين آخرين داخل المركز وتحديد صلاحياتهم بدقة:
  - موظف حجز: يرى الطلبات ويستطيع إنشاءها وتعيين الفنيين فقط.
  - موظف إداري: يرى التقارير المالية للمركز دون القدرة على التعديل.
- لا يستطيع أدمن المركز إنشاء حسابات بصلاحيات أعلى من صلاحياته.

### ج. إدارة الطلبات (داخل المركز فقط)

- **قائمة الطلبات:** تعرض فقط الطلبات المحولة لهذا المركز، مع الفلترة (بالحالة، الفني، التاريخ، نوع الجهاز).
- **تفاصيل الطلب:** بيانات العميل، نوع الجهاز وعطله، الموقع الجغرافي، الفني المعيّن، تاريخ تغييرات الحالة، قيمة الطلب.
- **تعيين فني:** اختيار فني من فنيي المركز فقط وتكليفه بالطلب.
- **تعديل قيمة الطلب:** أدمن المركز يستطيع تحديث المبلغ النهائي قبل الإغلاق المالي.
- **إعادة فتح طلب:** في حالة وجود مشكلة بعد الاكتمال (مرتبط بنظام المتابعة).

### د. الإدارة المالية للمركز

- **محفظة المركز:** عرض الأرقام الثلاثة (إجمالي التحصيل، المستحق للمنصة، الصافي) — للعرض فقط، لا يمكن التعديل.
- **نسبة العمولة:** تُعرض للمركز للاطلاع فقط، لا يمكن تعديلها.
- **سجل الطلبات المالي:** قائمة بالطلبات المكتملة مع قيمة كل منها وقيمة العمولة المستقطعة.
- **سجل التسويات:** تاريخ التسويات التي أجراها السوبر أدمن مع المركز.
- **التقارير:** ملخص مالي يومي وشهري.

### هـ. التقارير والإحصاءات

- عدد الطلبات (حسب الحالة، حسب الفني، حسب المنطقة).
- متوسط وقت إغلاق الطلبات.
- أكثر أنواع الأعطال شيوعاً.
- أداء الفنيين مقارنةً ببعضهم.

## خامساً: واجهة الفني

الفني يملك واجهة مبسطة (تطبيق جوال أو web بسيط) تركز على ما يحتاجه في الميدان فقط.

### ما يراه الفني

- قائمة الطلبات المعيّنة له شخصياً فقط، مرتبة بالتاريخ.
- تفاصيل كل طلب: اسم العميل، رقم هاتفه، العنوان، نوع الجهاز، وصف العطل، وأي ملاحظات من المركز.
- حالة كل طلب.

### ما يستطيع الفني فعله

- **تغيير حالة الطلب:** من "قيد الانتظار" إلى "قيد التنفيذ" عند وصوله للعميل، ومن "قيد التنفيذ" إلى "مكتمل" عند الانتهاء.
- **إضافة ملاحظات:** تسجيل ما تم فعله بالضبط، وأي قطع غيار استُخدمت.
- **رفع صور:** صور الجهاز قبل وبعد الإصلاح (اختياري لكن موصى به).
- **إدخال المبلغ النهائي:** في حالة أُعطي صلاحية ذلك من أدمن المركز.

### ما لا يراه الفني أبداً

- أي طلب خاص بمركز آخر.
- أي طلب داخل مركزه غير معيّن له شخصياً.
- البيانات المالية للمركز أو العمولات.

## سادساً: واجهة موظف الكول سنتر

موظف تابع للمنصة، يعمل فقط على نظام المتابعة.

### ما يراه

- قائمة العملاء المستحقين للمتابعة (الطلبات التي مضى عليها X يوم من الاكتمال).
- بيانات العميل ورقم هاتفه.
- تفاصيل الطلب الذي أُتمّ.
- سجل المحاولات السابقة على نفس الطلب.

### ما يستطيع فعله

- تسجيل محاولة اتصال (حتى لو ما ردش أحد).
- تسجيل نتيجة المكالمة: راضٍ / غير راضٍ / لا يوجد رد.
- في حالة "راضٍ": تسجيل تقييم الفني (ممتاز / جيد / مقبول).
- في حالة "غير راضٍ": رفع الأمر لأدمن المركز أو السوبر أدمن لاتخاذ قرار إعادة الفتح.
- تحديد موعد محاولة اتصال أخرى لو ما ردش.

## سابعاً: العميل عبر API

العميل لا يملك لوحة تحكم، بل يتفاعل عبر مجموعة من الـ API endpoints التي سيستهلكها تطبيق الجوال مستقبلاً.

### أ. التسجيل والمصادقة (Authentication APIs)

- **تسجيل حساب جديد:** الاسم الكامل، رقم الهاتف (يُستخدم كمعرّف أساسي)، البريد الإلكتروني (اختياري)، كلمة المرور.
- **تسجيل الدخول:** برقم الهاتف وكلمة المرور. يُعاد رمز JWT.
- **التحقق برقم الهاتف:** OTP يُرسل عبر SMS عند التسجيل.
- **تسجيل الخروج:** إلغاء رمز JWT.
- **استعادة كلمة المرور:** عبر OTP على رقم الهاتف.

### ب. الملف الشخصي (Profile APIs)

- **عرض الملف الشخصي:** البيانات الأساسية، عناوينه المحفوظة.
- **تحديث البيانات:** الاسم، البريد الإلكتروني، رقم الهاتف (مع إعادة التحقق).
- **إدارة العناوين:** إضافة، تعديل، حذف عنوان. كل عنوان له اسم مختصر (المنزل / العمل)، نص كامل، وإحداثيات جغرافية (Lat/Long).

### ج. الطلبات (Orders APIs)

- **إنشاء طلب جديد:**
  - نوع الجهاز (مثلاً: غسالة، تكييف، ثلاجة).
  - الماركة والموديل (اختياري).
  - وصف العطل بالنص.
  - صور العطل (اختياري، رفع ملفات).
  - عنوان الخدمة (من عناوينه المحفوظة أو عنوان جديد).
  - الوقت المفضل للزيارة (تاريخ وفترة الوقت: صباح / مساء).
- **عرض طلباته:** قائمة بجميع طلباته مع حالة كل منها.
- **تفاصيل طلب بعينه:** الحالة الحالية، اسم الفني المعيّن، الوقت المتوقع، المبلغ بعد الاكتمال، الملاحظات.
- **تتبع حالة الطلب:** الحالة تتحدث بشكل realtime أو عند كل fetch.
- **إلغاء طلب:** مسموح فقط إذا كان الطلب في حالة "قيد الانتظار" ولم يُعيّن له فني بعد.

### د. الإشعارات (Notifications APIs)

- الحصول على قائمة الإشعارات.
- تحديد الإشعار كـ "مقروء".
- **أحداث تُطلق إشعاراً للعميل:**
  - تم استلام طلبك.
  - تم تعيين فني لطلبك (مع اسم الفني).
  - الفني في طريقه إليك (عند تغيير الحالة لـ "قيد التنفيذ").
  - تم إتمام طلبك (مع المبلغ النهائي).

### هـ. التقييم (Rating APIs) — مرتبط بنظام المتابعة

- بعد اتصال الكول سنتر، قد يُطلب من العميل تقييم التجربة عبر التطبيق.
- تقييم الخدمة برقم من 1 إلى 5.
- تقييم الفني.
- تعليق نصي اختياري.

## ثامناً: دورة حياة الطلب الكاملة

### المرحلة الأولى (بدون تطبيق عميل)

```
موظف استقبال (أو السوبر أدمن) يتلقى طلباً بالهاتف
       ↓
يُنشئ الطلب يدوياً في النظام
       ↓
النظام يرشح المراكز المتاحة (حسب الموقع ونوع الجهاز)
       ↓
السوبر أدمن أو أدمن المركز يختار المركز المناسب ويحول الطلب
       ↓
أدمن المركز يعيّن الفني
       ↓
الفني يرى الطلب في واجهته ويبدأ التنفيذ
```

### المرحلة الثانية (مع تطبيق العميل)

```
العميل يسجّل الطلب عبر API التطبيق
       ↓
النظام يحدد المركز المناسب تلقائياً (أو يعرضه للسوبر أدمن للمراجعة)
       ↓
المركز يستقبل الطلب في لوحة التحكم
       ↓
أدمن المركز يعيّن الفني
       ↓
العميل يستقبل إشعاراً باسم الفني
       ↓
الفني يُغير الحالة ميدانياً
       ↓
العميل يتتبع الحالة realtime
```

### حالات الطلب (Order Statuses) — بالتسلسل

| الحالة                    | من يُغيّرها      | الشرط                |
| ------------------------- | ---------------- | -------------------- |
| معلّق (Pending)           | النظام           | عند الإنشاء تلقائياً |
| محوّل للمركز (Dispatched) | السوبر أدمن      | بعد اختيار المركز    |
| معيّن للفني (Assigned)    | أدمن المركز      | بعد تعيين الفني      |
| قيد التنفيذ (In Progress) | الفني            | عند وصوله للعميل     |
| مكتمل (Completed)         | الفني            | عند إنهاء الخدمة     |
| ملغى (Cancelled)          | العميل أو الأدمن | في حالات محددة       |
| معاد فتحه (Reopened)      | الأدمن           | بعد شكوى في المتابعة |

## تاسعاً: المنطق المالي التفصيلي

### بنية محفظة المركز

محفظة كل مركز تتكون من ثلاثة أرقام مستقلة تتحرك بشكل مستقل:

**١. إجمالي التحصيل (Total Collected)**
يزداد فقط عند إغلاق طلب مكتمل. لا ينقص أبداً إلا في حالة إلغاء معاملة (Reversal) بقرار من السوبر أدمن.

**٢. مستحق للمنصة (Platform Due)**
يزداد بمقدار (قيمة الطلب × نسبة العمولة) عند كل طلب مكتمل. ينقص عند إجراء تسوية (يدفع المركز للمنصة).

**٣. صافي المركز (Center Net)**
لا يُخزن كرقم منفصل في قاعدة البيانات، بل يُحسب دائماً:
`الصافي = إجمالي التحصيل - مستحق للمنصة`

### آلية الإغلاق المالي التلقائي

عند تغيير حالة الطلب إلى "مكتمل":

1. النظام يقرأ نسبة عمولة المركز.
2. يحسب قيمة العمولة: `قيمة الطلب × نسبة العمولة`.
3. يضيف قيمة الطلب كاملة إلى "إجمالي التحصيل".
4. يضيف قيمة العمولة إلى "مستحق للمنصة".
5. يُسجّل سجل مالي (Transaction Log) يربط هذه العملية بالطلب تحديداً.

### التسوية (Settlement)

التسوية سجل مالي يحتوي على:

- تاريخ التسوية.
- المبلغ المُسوَّى.
- نوع التسوية: (المنصة تحصّل من المركز) أو (المنصة تدفع للمركز).
- ملاحظات (طريقة الدفع، رقم مرجعي).
- من أجرى التسوية (السوبر أدمن).

بعد التسوية، ينخفض "مستحق للمنصة" بمقدار قيمة التسوية.

### الإيقاف التلقائي

- الإعدادات تحتوي على رقم يسمى "حد الإيقاف" (مثلاً: 5000 جنيه).
- عند كل إغلاق مالي لطلب، النظام يتحقق: هل "مستحق للمنصة" لهذا المركز تجاوز حد الإيقاف؟
- إذا نعم، يتغير status المركز تلقائياً إلى "موقوف".
- المركز الموقوف لا يظهر كخيار عند توزيع الطلبات الجديدة.
- لا يُستأنف إلا بعد التسوية **وقرار يدوي** من السوبر أدمن.

## عاشراً: نظام المتابعة التفصيلي

### منطق الظهور في قائمة المتابعات

الطلب يظهر في قائمة المتابعات إذا تحققت **كل** الشروط الآتية:

1. حالة الطلب = "مكتمل".
2. مضى على الاكتمال عدد الأيام المحددة في الإعدادات (X يوم) أو أكثر.
3. لم يُجرَ عليه متابعة ناجحة (مكالمة وصل فيها للعميل) بعد.

### دورة المتابعة

1. الطلب يظهر في القائمة.
2. الكول سنتر يتصل ويسجل محاولة:
   - **لا يرد:** تُسجل محاولة بدون رد، ويُجدوَل اتصال آخر.
   - **يرد وراضٍ:** يُغلق الطلب من المتابعات، يُعطى الفني تقييم إيجابي.
   - **يرد وغير راضٍ:** يُصعَّد الأمر، الأدمن يقرر.

### تصعيد المشاكل

عند إبلاغ عميل عن مشكلة، الأدمن (مركز أو سوبر) لديه خيارات:

- **إعادة فتح الطلب:** نفس الطلب يتغير حالته لـ "معاد فتحه"، يعود للمركز لحل المشكلة.
- **جدولة زيارة جديدة:** إنشاء طلب جديد مرتبط بالطلب الأصلي كـ "زيارة ضمانية".
- **رفض الشكوى:** مع تسجيل السبب (قرار بشري).

## حادي عشر: HR والمصاريف التفصيلية

### إدارة موظفي المنصة

- كل موظف له: الاسم، الوظيفة، الراتب الأساسي، تاريخ التعيين.
- **البدلات:** مبالغ إضافية بأسباب (بدل انتقال، حوافز أداء).
- **الخصومات:** مبالغ مستقطعة بأسباب (غيابات، سلف).
- **صرف الراتب:** إجراء شهري يسجل الراتب النهائي = الأساسي + البدلات − الخصومات.

### المصاريف التشغيلية

- كل مصروف له: التاريخ، النوع (إيجار / كهرباء / إعلانات / صيانة / أخرى)، المبلغ، ملاحظة.
- تُجمع شهرياً لحساب إجمالي التكاليف.

### معادلة صافي ربح المنصة (شهرياً)

```
صافي ربح المنصة = إجمالي العمولات المحصّلة خلال الشهر
                 − إجمالي رواتب موظفي المنصة
                 − إجمالي المصاريف التشغيلية
```

## ثاني عشر: القواعد الحاكمة والصلاحيات (ملخص)

| القاعدة               | التفصيل                                                          |
| --------------------- | ---------------------------------------------------------------- |
| عزل الفني             | الفني لا يرى إلا طلباته الشخصية داخل مركزه. التطبيق في كل query. |
| عزل المركز            | أدمن المركز لا يرى أي بيانات مركز آخر.                           |
| العمولة readonly      | المركز يعرضها، السوبر أدمن فقط يعدّلها.                          |
| الإغلاق المالي تلقائي | لا تدخل بشري عند إغلاق الطلب.                                    |
| المتابعة بشرط الوقت   | لا تُعرض إلا بعد مرور المدة. الفلتر في كل fetch.                 |
| الإيقاف التلقائي      | يتحقق عند كل إغلاق مالي. يحتاج تدخلاً لاستئنافه.                 |
| إلغاء الطلب           | العميل يلغي فقط في "معلّق". بعد التعيين: الأدمن فقط.             |
| الزيارة الضمانية      | طلب جديد مرتبط بالأصلي، لا يُعدّ دخلاً جديداً إذا كانت مجانية.   |
| صلاحيات موظف المركز   | لا يتجاوز صلاحيات أدمن المركز الذي أنشأه.                        |

## ثالث عشر: نقاط تقنية جوهرية (بدون كود)

### متعدد المستأجرين (Multi-tenancy)

كل مركز له نطاق بيانات معزول. يُمكن تطبيقه بـ:

- **عمود في الجداول (Column-based):** كل صف فيه `center_id` للتمييز. أسهل في الإعداد.
- **قاعدة بيانات منفصلة (DB-per-tenant):** عزل كامل. أقوى لكن أثقل.

### الإشعارات الـ Realtime

تحديث حالة الطلب للعميل يتطلب آلية Push، سواء عبر:

- Firebase Cloud Messaging (FCM) لتطبيق الجوال.
- WebSockets أو Server-Sent Events للواجهة الويب.

### نقاط الـ API الحساسة

- كل endpoint للعميل يحتاج التحقق من هوية العميل (JWT).
- الطلبات تُفلتر دائماً بـ `customer_id` من رمز JWT، لا من الـ request body.
- لا يمكن للعميل تمرير `customer_id` آخر في الطلب والوصول لبياناته.
